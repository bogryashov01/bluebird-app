# Bluebird Mobile cleanup map: Clerk + production API

**Purpose:** Source-based inventory and safe future cleanup plan for moving Bluebird Mobile from the local/demo API client to the intended Clerk-authenticated API at `https://bluebirdjets.com/api`.

**Scope and evidence:** Static review of the Bluebird mobile source, the separate checked-in local API server where relevant, `CLERK-MEMBER-JOURNEY-AUDIT.md`, `AUTHENTICATED-API-READINESS.md`, and the supplied `attached_assets/0_BLUEBIRD_MOBILE_PRODUCTION_API_CONTRACT_1791817009725.md` (source snapshot dated 2026-10-12). The supplied contract says production runtime was not tested. This report does not establish deployed behavior. No authenticated or other production API request, Clerk sign-in, SMS, build, or account operation was performed. No application, API, auth, Clerk, account, or deployment setting was changed.

## Decision labels

- **Retire** — legacy-only infrastructure or an old route can be removed after its active demo/local consumers have been migrated or explicitly retired.
- **Replace/adapt** — retain its purpose, UI, or useful boundary, but replace local API/auth assumptions and data shapes.
- **Preserve** — reusable product UI or a production-client foundation; keep it and integrate deliberately.
- **Retain until prerequisite is verified** — do not connect or remove it until the named API, security, policy, or runtime condition is evidenced.

These labels describe a possible future cleanup, not changes made by this report.

## Summary

Bluebird has two distinct paths today:

1. **Local/demo path:** the generated `@workspace/api-client-react` client targets the development API origin configured by `EXPO_PUBLIC_DOMAIN`; its legacy auth and member routes use a Bluebird JWT stored with a cached Bluebird user. Mobile screens, mutations, queue observers, and member-data hooks still consume that API. This path is active when Clerk mode is off and local flight-read mode is selected.
2. **Clerk migration path:** Clerk phone-code sign-in/sign-up is available only behind the explicit development gate. It establishes a Clerk session, but it does not resolve that identity to an authoritative Bluebird member. `AuthContext` suppresses the legacy user/JWT in Clerk mode, the global legacy token getter returns `null`, `memberAccessResolved` stays false, and route guards keep member screens closed. The signed-in page is an intentional pending-link notice.

The production client foundations already include a fresh-token adapter, a validated `https://bluebirdjets.com/api` base, request/error parsing, public production flight reads, and an always-unavailable authenticated-access gate. They are not yet a complete mobile integration. No screen constructs or calls `createAuthenticatedProductionApiClient`; the signed-in page only prepares a token provider. Most existing authenticated screens still call generated local-client hooks, and several feature families have no corresponding operation in the supplied production contract.

**Target flow:** Clerk session → obtain a fresh `getToken()` for each request → send only `Authorization: Bearer <token>` to `https://bluebirdjets.com/api` → receive an explicit, authoritative Bluebird-member resolution → clear/namespace member caches by resolved identity → route a linked member to the existing screens, or route an explicitly confirmed new/incomplete account through the supported production profile/onboarding flow. There must be **no local-server fallback** in this Clerk production path and no inference of “new member” from a missing token, error, anonymous-shaped `/api/me` response, empty profile, or matching phone/email alone.

## 3. Intended target architecture and required resolver behavior

1. **Clerk owns authentication.** Keep Clerk Expo token-cache/session ownership. Do not persist Clerk access tokens in `bluebird_token`, pass them through the legacy global token getter, or combine Clerk and demo identities in one unqualified cache.
2. **Ask Clerk for a fresh token per explicit production request.** Reuse the isolated `clerkProductionTokenProvider` boundary. The API owner must confirm whether the default Clerk session token is accepted or a named template is required, plus issuer, audience/authorized-party, claims, and intended Clerk instance.
3. **Use one production API client only.** Construct the authenticated client with `https://bluebirdjets.com/api`, `credentials: 'omit'`, and the injected verified token provider. Do not use `EXPO_PUBLIC_DOMAIN`, the generated local client's global token getter, cookies, or local-server fallback for production member requests.
4. **Resolve a Bluebird identity authoritatively.** The resolver must return a backend-defined, typed result proving the linked Bluebird member identity and status. The supplied `GET /api/me` projection has no `userId`; it can return an anonymous-shaped HTTP 200 on normal anonymous access and caught identity/database/schema failures. Therefore `isMember: false`, `isAuthenticated: false`, empty profile defaults, `needsSignupPhone`, 401/403/404 without confirmed semantics, timeouts, and malformed responses are not proof of “new member.”
5. **Separate resolution states.** Model at least loading, linked member, explicitly new/unlinked Clerk identity, linked-but-profile-incomplete/onboarding-required, authentication/backend error, and retryable network/timeout/cancel. Only the backend's explicit new/unlinked result may start a new-account path. Phone/email matching alone is not authorization to claim a legacy record.
6. **Bind member state to the resolved identity.** Clear member query state before switching Clerk identity, signing out, or changing resolved Bluebird member. Do not set member access true until the authoritative response is validated. Cache keys should include the verified member identifier and never a bearer token.
7. **Route existing members to existing screens.** Preserve the tabs and detail UI, but adapt each feature's data client, model, action and error handling to the production contract. Keep unsupported features unavailable or local-demo-only rather than silently sending them to the old server.
8. **Route a confirmed new or incomplete identity through supported production profile flow.** The supplied contract describes `PUT /api/me/profile` as a full profile write, not local short registration or `PATCH /api/auth/me`. It requires profile facts such as first/last name, date of birth, gender, home airport, favorite city keys, and policy-dependent verified phone; consent/preferences have separate rules. Obtain explicit backend confirmation whether the call creates a profile, how it links a new identity, and what onboarding outcome is authoritative.

### Current safety gates to preserve

- Clerk provider/routes are opt-in and guarded by `lib/clerkAuthConfig.ts`; the existing configuration is development-only and test-key constrained according to `AUTHENTICATED-API-READINESS.md`.
- `AuthContext` clears and withholds legacy token/user when Clerk mode is on; `createLegacyAuthTokenGetter` returns `null` in that mode.
- Root/tab route guards deny member routes while `memberAccessResolved` is false.
- `PRODUCTION_AUTH_AVAILABILITY` remains `unavailable`.
- Production-client and Clerk-bridge tests use mocked sessions/fetchers. They verify local logic only and are not proof of production API acceptance or iOS/Android session behavior.

## 5. Ordered cleanup plan and validation gates

This sequence is intentionally dependency-safe. Do not start by deleting legacy files or swapping the shared generated API package.

1. **Freeze and document the boundary (this report).** Keep the Clerk production gate unavailable; preserve the demo/local path and all screens. Confirm source references and the contract revision with the API owner without making API requests.

Resolve `/api/me`'s anonymous-shaped-200 ambiguity or define a dedicated resolver. Verify the contract on an approved non-production deployment.
