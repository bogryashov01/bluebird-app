TASK: BLUEBIRD MOBILE — RESOLVE CLERK COMPATIBILITY VIA EXPO BASELINE

MODE: BUILD / EXECUTE

PROJECT: Bluebird Mobile (Expo / React Native)

CONTEXT:

Task #325 confirmed that Clerk Expo SDK cannot be
safely installed on the current dependency baseline.

Current versions:

- Expo SDK 54.0.37
- React 19.1.0
- React DOM 19.1.0
- React Native 0.81.5

Tested Clerk versions:

- @clerk/expo@4.10.1
- @clerk/expo@3.0.0
- @clerk/expo@2.19.0

All produced incompatible React peer dependencies.

The previous isolated Clerk installation also caused
all five startup tests to fail with a React useState error.

The unchanged workspace passes those tests.

GOAL:

Find a stable, officially supported dependency
combination that allows Clerk authentication to work
without breaking Bluebird Mobile.

IMPORTANT:

Do not modify the main working tree until a
candidate passes all isolated compatibility checks.

PHASE 1 — RESEARCH

Inspect the current project dependencies.

Determine:

1. The latest stable Expo SDK officially available.
2. Its supported React version.
3. Its supported React Native version.
4. Compatible React DOM version.
5. Compatible stable @clerk/expo version.
6. Required Clerk peer dependencies.
7. Compatibility with the existing Expo Router.
8. Compatibility with the existing native modules.

Use official Expo and Clerk compatibility documentation
and actual package peer dependency metadata.

Do not assume that a successful pnpm install proves
compatibility.

PHASE 2 — ISOLATED UPGRADE

Create a disposable worktree.

Test the smallest officially supported Expo baseline
change that resolves Clerk's React peer requirements.

Do not automatically select the newest Expo SDK
if a smaller supported change is sufficient.

Install the candidate dependencies only in the
isolated worktree.

Do not use:

- --force
- --legacy-peer-deps
- Peer dependency overrides
- Suppressed peer warnings
- Unstable or canary releases

PHASE 3 — COMPATIBILITY TESTS

Run the following checks in the isolated worktree:

1. Dependency resolution with no relevant peer conflicts.
2. Expo dependency validation.
3. Library TypeScript checks.
4. Bluebird application TypeScript checks.
5. All 15 production authentication API tests.
6. All five startup stability tests.
7. Network reliability tests.
8. Membership and queue regression tests.
9. Passenger flow tests.
10. Metro export for web, iOS and Android.
11. git diff --check.

Investigate any React useState errors.

Check for:

- Duplicate React installations
- React renderer version mismatches
- Incorrect package resolution
- Multiple React copies in the workspace

Do not classify the candidate as compatible if
the startup tests fail.

PHASE 4 — NATIVE READINESS

Check whether the candidate supports:

- iOS development builds
- Android development builds
- Expo SecureStore
- Clerk token caching
- OAuth redirects
- Expo Router integration

If native builds cannot be performed in Replit,
document that limitation explicitly.

Do not claim native compatibility without
native verification.

PHASE 5 — IMPLEMENTATION DECISION

If a stable candidate passes all available checks:

- Document the exact compatible dependency versions.
- Document the required migration changes.
- Identify any remaining native verification.
- Prepare a precise implementation plan.

Do NOT apply the upgrade to the main working tree yet.

Wait for explicit approval before changing the
main project's Expo, React or React Native versions.

If no compatible candidate passes:

- Leave the main project unchanged.
- Explain the exact blockers.
- Identify the smallest viable alternative.

Provide:
