BLUEBIRD MOBILE — QUEUE MVP + DEVELOPMENT TEST FLOW

PRIORITY: HIGH
MODE: BUILD / EXECUTE

GOAL:

Implement and verify the Queue experience
in the Bluebird Mobile application.

We need a functional Queue MVP that can
use the existing Main Bluebird API.

We also need a safe development-only
preview to test the full Queue UI when
no eligible live flight is available.

SCOPE:

Bluebird Mobile ONLY.

Do not modify Main Bluebird Website,
Main API, database, Clerk backend,
or production configuration.

==================================================
1. INSPECT EXISTING QUEUE IMPLEMENTATION
==================================================

Before editing, inspect:

- Discover flight cards
- Flight Details screen
- Existing Join Queue button
- Existing Queue API client
- Trips screen
- Existing queue status screens
- Membership eligibility handling
- Authentication handling
- Existing Queue tests

Determine what is already implemented
and what is missing.

Do not rebuild working functionality.

==================================================
2. LIVE QUEUE FLOW
==================================================

Implement the supported live flow:

Discover
→ Flight Details
→ Join Queue
→ Queue Confirmation
→ Trips / Queue Status

Use only the existing authenticated
Main Bluebird API.

Do not invent API endpoints.

Do not invent queue eligibility rules.

Do not assume all flights allow joining.

The Join Queue button must reflect
real backend eligibility.

If joining is unavailable, show
a clear user-friendly explanation.

Do not send passengerCount or other
unsupported fields in queue requests.

==================================================
3. JOIN QUEUE
==================================================

When a user taps Join Queue:

- Check the real authenticated state
- Check existing membership/eligibility data
- Use the supported queue API request
- Show a loading state
- Prevent duplicate submissions
- Handle API errors
- Show success only after API confirmation

Do not display a successful queue join
based on local state alone.

If a user is already in the queue,
show the existing queue status instead
of submitting another join request.

Do not silently create a reservation.

==================================================
4. QUEUE STATUS
==================================================

Display real information returned by API.

Examples, only when supported:

- Flight route
- Departure date/time
- Aircraft
- Queue participation status
- Relevant next action

Do not invent:

- Queue position
- Number of competitors
- Probability of winning
- Winner status
- Reservation confirmation
- Pricing
- Payment requirements

If a field is unavailable, omit it.

==================================================
5. TRIPS INTEGRATION
==================================================

Make queue participation discoverable
from the existing Trips screen.

If the API provides the user's
queue entries, display them.

Each entry should open the relevant
Queue / Flight Details screen.

If no queue entries exist, show
a polished empty state.

Do not fabricate trips.

Preserve existing Trips functionality.

==================================================
6. DEVELOPMENT-ONLY QUEUE PREVIEW
==================================================

Add a safe Queue Preview mode
for development testing.

IMPORTANT:

This is NOT a real booking flow.

Requirements:

- Available only in development builds
- Never enabled in production
- Clearly labeled "DEMO"
- Uses isolated fixture data
- Never calls queue mutation endpoints
- Never modifies Main Bluebird
- Never creates reservations
- Never changes membership or payment state

Provide a simple developer entry point
to preview:

A. Flight Details — eligible
B. Join Queue — loading
C. Queue Confirmation
D. Queue Status — waiting
E. Queue Status — unavailable
F. Queue Status — selected/winner,
   only as an explicitly simulated UI state

Demo data must never be mixed with
real Trips or Discover API results.

If possible, use the existing
development preview infrastructure.

Do not add demo entries to the
real authenticated user's account.

==================================================
7. DESIGN
==================================================

Match the approved Bluebird visual style.

Use:

- Light backgrounds for detail screens
- Navy text
- Blue primary actions
- Rounded white cards
- Compact spacing
- Clear status indicators
- Native iOS loading states

Avoid:

- Technical API messages
- Large empty gaps
- Fake statistics
- Excessive explanatory text
- Unnecessary screens

The Queue experience should feel like
a real premium aviation booking app.

==================================================
8. ERROR HANDLING
==================================================

Handle:

- User not authenticated
- No active membership
- Flight not eligible
- Queue closed
- Already joined
- API unavailable
- Network timeout
- Unexpected backend response

Use backend-supported error states.

Do not invent eligibility requirements
or silently redirect to Discover.

Preserve the user's current screen
when an API request fails.

==================================================
9. NAVIGATION
==================================================

Verify:

Discover → Flight Details

Flight Details → Queue

Queue → Trips

Trips → Queue Details

Back navigation must work correctly.

No unexpected redirects to Discover.

Preserve the existing Profile navigation
fixes from Task #581.

==================================================
10. TESTING
==================================================

Run Mobile TypeScript checks.

Run existing relevant tests.

Add focused tests for:

- Eligible flight
- Ineligible flight
- Already joined
- Successful queue join
- Failed queue join
- Duplicate tap prevention
- Queue status rendering
- Trips navigation
- Demo mode isolation
- Production demo exclusion

Do not claim live API verification
if authenticated testing was not performed.

==================================================
11. DELIVERY
==================================================

Implement directly.

Report:

1. Existing Queue functionality found
2. Missing functionality implemented
3. Queue API endpoints actually used
4. Files modified
5. Tests passed
6. Demo preview entry point
7. Live flow verification status
8. Remaining backend limitations

Do not stop at an audit.

Do not modify Main Bluebird.

Do not invent backend capabilities.

Focus on a working, testable Queue MVP.
