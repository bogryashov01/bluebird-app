The goal is to make the EXISTING WEB PREVIEW display REAL production

==================================================
TARGET FLOW
==================================================

The exact test flow is:

Replit Web Preview
→ existing local/demo sign-in
→ Discover
→ REAL production Bluebird flights
→ open a flight
→ REAL production Flight Details
→ REAL airport coordinates/data
→ route visible on the web map

The local/demo authentication is allowed ONLY to pass the current UI auth gate.

Flight data MUST NOT come from the local prototype API or fixtures.

==================================================
1. FIX THE WEB PREVIEW START MODE
==================================================

The previous audit found that the normal dev command explicitly sets:

EXPO_PUBLIC_BLUEBIRD_FLIGHT_READ_MODE=local

That is NOT acceptable for this test.

Configure/start the current Replit Web Preview so that the Expo app receives:

EXPO_PUBLIC_BLUEBIRD_FLIGHT_READ_MODE=production

Do not globally redesign environment configuration.

A minimal development/run configuration change is allowed if necessary so
that Replit Web Preview can run Stage 1 against production reads.

Do NOT change production API URLs.

Production API base:

https://bluebirdjets.com/api

==================================================
2. VERIFY THE DATA SOURCE
==================================================

Once the web app is running, verify that Discover uses:

GET https://bluebirdjets.com/api/empty-legs

Flight Details uses:

GET https://bluebirdjets.com/api/empty-legs/:id

Airport metadata uses:

GET https://bluebirdjets.com/api/airports?codes=...

There must be NO silent fallback to local/demo flight fixtures.

Local prototype authentication may still be used.

This combination is expected during this temporary test:

AUTH = local/demo
FLIGHTS = production
AIRPORTS = production

==================================================
3. USE THE EXISTING WEB PREVIEW
==================================================

Run the application in the existing Replit Web Preview / Simulate on Web.

Use the existing local/demo sign-in flow if needed to reach Discover.

Do not create or modify a production account.

Once signed in, navigate to Discover.

==================================================
4. VISUALLY VERIFY DISCOVER
==================================================

Do not stop at unit tests or API inspection.

Verify the rendered Web Preview.

Confirm that production flight cards are actually visible.

For three visible flights, compare the rendered card with the anonymous
production API response.

Only compare/report these safe fields:

- numeric flight ID
- origin airport code
- destination airport code
- departure date/time
- aircraft type

The values shown in the UI must correspond to the production response.

==================================================
5. VERIFY FLIGHT DETAILS
==================================================

Open one of the visible production flights.

Confirm that the app requests:

GET /api/empty-legs/:id

using the SAME numeric production flight ID.

Compare:

- origin
- destination
- departure time
- arrival time
- aircraft type

between the production response and the rendered Flight Details screen.

==================================================
6. VERIFY AIRPORT DATA + WEB MAP
==================================================

For that same flight, verify airport metadata comes from:

GET /api/airports?codes=ORIGIN,DESTINATION

Confirm the map receives the production:

- latitude
- longitude
- timezone

for both airports.

Then verify visually in Web Preview that:

- origin is represented
- destination is represented
- route/map is visible

Do not use hardcoded coordinates or local airport fixtures.

==================================================
7. NETWORK PROOF
==================================================

Inspect the Web Preview/browser network activity if available.

Confirm requests are going to:

bluebirdjets.com/api/empty-legs
bluebirdjets.com/api/empty-legs/:id
bluebirdjets.com/api/airports

and NOT to the local prototype flight endpoint for Stage 1 flight data.

Local API requests used only for demo authentication are acceptable.

==================================================
8. IF SOMETHING IS BROKEN
==================================================

Unlike the previous task, you MAY make a SMALL Stage 1 fix if it is necessary
to make production data render correctly in Web Preview.

Examples:

- Web Preview starts with the wrong flight read mode
- environment variable is not reaching Expo Web
- web map receives the wrong data source
- production adapter causes a rendering error
- CORS/config issue that can safely be fixed client-side

Do not perform a large refactor.

Do not touch Stage 2 authentication.

After any small fix, rerun the Web Preview and verify visually again.

==================================================
9. TESTS
==================================================

After the Web Preview works, run the focused Stage 1 tests and TypeScript
check.

All production requests in this task must be anonymous GET requests.
