TASK: Verify Clerk Authentication with Bluebird API Without iOS

PROJECT: Bluebird Mobile

CONTEXT:

Clerk SMS authentication works in the
Bluebird Mobile web Preview.

A fresh Clerk session token is available
through the Clerk SDK.

The browser diagnostic fails at Fetch with:

Failure: browser transport (ambiguous)

The developer cannot currently access
the Apple Developer account.

GOAL:

Verify whether the existing Bluebird
production API accepts the Clerk
Development session token.

Do not require an iOS build.

APPROACH:

Create a temporary, Development-only,
server-side diagnostic inside the
Bluebird Mobile Replit environment.

The diagnostic must make exactly one
server-side request to:

GET https://bluebirdjets.com/api/me

using a fresh Clerk token obtained
from the existing signed-in session.

SECURITY REQUIREMENTS:

1. Do not modify the main Bluebird backend.

2. Do not modify production data.

3. Do not change Clerk configuration.

4. Do not deploy the diagnostic.

5. Do not store JWTs in files, logs,
   environment variables, or databases.

6. Do not display JWTs or Authorization
   headers.

7. Never accept arbitrary target URLs.

8. Never create an unrestricted proxy.

9. The diagnostic must be disabled
   outside Development.

10. Require explicit user confirmation
    before any production API request.

11. Protect the diagnostic endpoint
    against unauthorized callers.
    Do not rely on a Development flag alone.

12. Accept only the minimum required
    authentication information.

13. Forward the token only to the fixed
    Bluebird production API endpoint.

14. Return only sanitized fields:
    - HTTP status
    - authentication accepted
    - isAuthenticated
    - isMember
    - isProfileComplete
    - schema validity
    - sanitized error category

15. Do not enable member access
    or modify navigation based on
    the diagnostic result.

IMPLEMENTATION:

First inspect the current Bluebird Mobile
Replit architecture and identify whether
a suitable private Development-only
server runtime already exists.

If a safe diagnostic endpoint can be
implemented without exposing tokens
or introducing an unauthenticated proxy,
implement it with mocked tests.

If the existing runtime cannot securely
support this approach, stop and explain
the smallest safe alternative.

Do not create another authentication system.

Do not use the legacy Bluebird JWT backend.

Do not execute any live authenticated
production request during implementation.

DELIVERABLE:

Provide a manual test button or workflow
that allows the signed-in developer
to explicitly run one server-side
Clerk-to-Bluebird API compatibility test.

Show only sanitized results.

Run TypeScript and mocked tests.
