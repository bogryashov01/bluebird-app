BLUEBIRD MOBILE — PRELOADED AIRPORT & CITY LISTS
WITH SELECTED ITEMS FIRST

PROJECT: Bluebird Mobile ONLY

PRIORITY: HIGH

THIS IS A FOCUSED UI AND DATA-LOADING TASK.

CRITICAL:

Main Bluebird Website, Main API, database,
Clerk configuration and Production are READ-ONLY.

Do not modify backend code.

Do not change authentication, profile saving,
membership logic, or existing navigation.

CURRENT PROBLEM:

On Step 2 of 3 — Locations:

1. Airports are not displayed until the user
   types something into the search field.

2. Cities do not display a useful browseable
   list immediately.

3. Already-selected items are not consistently
   visible at the top.

4. The user wants to browse, scroll, search,
   and select items without being forced to search.

GOAL:

Make Airports and Cities behave like normal,
preloaded, scrollable selection lists.

Keep the existing Bluebird Mobile design.

STEP 1 — INSPECT EXISTING DATA SOURCES

Inspect the existing Mobile code and available
Main API contracts.

Known endpoints:

GET /api/airports/search?q=...
GET /api/airports/cities
GET /api/airports?codes=...

Determine:

- Whether a complete airport catalog is available
- Whether airport browsing/pagination is supported
- Whether a local airport dataset already exists
- Whether the cities endpoint returns the full catalog
- How existing selected airport and city values
  can be resolved to display labels

Do not invent API endpoints.

Do not hardcode fake airport or city data.

STEP 2 — AIRPORTS TAB

On initial screen load:

Display a scrollable list of available airports
WITHOUT requiring the user to type a search.

Order:

1. Selected home airport first
2. Other selected airports, if supported
3. Remaining airports

Show:

- Airport name
- Airport code
- City/location when available
- Selection control
- Selected-state highlighting

Provide a search field above the list.

Searching should filter or query available
airports without clearing current selections.

IMPORTANT:

The existing Main API supports one
homeAirportCode.

Use SINGLE SELECT for the persisted home airport.

Do not allow additional airport selections unless
an existing supported API field can persist them.

If multi-airport persistence is unsupported,
keep the UI honest and use one selected airport.

Do not store additional airports as unrelated
favorite cities.

Do not silently discard selections.

STEP 3 — CITIES TAB

Load the available city catalog when the
Locations screen opens.

Display a scrollable list immediately.

Order:

1. Already-selected cities first
2. Remaining available cities

Each row should show:
- City name
- Region/state
- Country
- Checkbox

Support:

- Multi-select
- Deselect
- Search
- Scrolling
- Selected-state highlighting

Use the existing favoriteCityKeys contract.

Preserve selections when switching tabs.

Do not automatically select random cities.

STEP 4 — SELECTED ITEMS

Selected values must always be visible at the
top of their respective lists.

Do not duplicate selected items elsewhere
in the same list.

When a user selects or deselects an item,
update the list ordering immediately.

When search is active:
- Keep selected values in form state
- Show matching search results
- Do not clear selections that are not visible

When the search is cleared:
- Restore selected-first ordering

STEP 5 — DATA LOADING

Avoid downloading an enormous airport dataset
if the existing API does not support it.

Prefer:

1. Existing supported catalog endpoint
2. Existing paginated browse endpoint
3. Existing real local airport dataset

If none are available:

- Always show already-selected airports
- Show a useful search-first state for
  additional airports
- Do not display a misleading connection error
- Report the exact API limitation

For Cities, use the existing city catalog.

Use efficient list rendering and avoid
unnecessary repeated requests.

STEP 6 — PRESERVE REGISTRATION

Do not modify:

- Personal Information
- Review & Save
- PUT /api/me/profile
- Clerk authentication
- Post-login routing
- Existing onboarding
- Membership restrictions

Do not change the existing profile payload.

STEP 7 — TESTING

Run TypeScript and focused tests.

Verify:

- Selected airport appears first
- Selected cities appear first
- Airport list displays without typing
  when a supported data source exists
- City list displays without typing
- Airport selection works
- City multi-select works
- Search works
- Scrolling works
- Switching tabs preserves selections
- No duplicate rows
- No fake airport data
- No unsupported API writes
- Existing profile save remains unchanged

IMPORTANT:

Do not claim full airport preload is implemented
if the backend only supports search.

If full browsing is unsupported, implement
the best safe fallback and report the limitation.
