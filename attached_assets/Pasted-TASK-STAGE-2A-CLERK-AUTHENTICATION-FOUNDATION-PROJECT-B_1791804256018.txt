TASK: STAGE 2A — CLERK AUTHENTICATION FOUNDATION

PROJECT: Bluebird Mobile App
ENVIRONMENT: Mobile Replit
FRAMEWORK: Expo / React Native / Expo Router

Prepare the Bluebird mobile application to reuse the existing
production Clerk authentication system used by bluebirdjets.com.

This is a FOUNDATION stage only.

Do NOT activate production Clerk authentication yet.

==================================================
IMPORTANT CONTEXT
==================================================

The existing Bluebird production backend already uses Clerk.

Production API:
https://bluebirdjets.com/api

Production frontend publishable key variable:
VITE_CLERK_PUBLISHABLE_KEY

Production backend publishable key variable:
CLERK_PUBLISHABLE_KEY

The mobile application will eventually use:
EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY

Production backend authentication:
Clerk session token sent via:

Authorization: Bearer <token>

The existing GET /api/me endpoint returns user authentication
and membership state.

However, the following remain UNVERIFIED:

- Production frontend/backend Clerk instance parity
- Enabled production Clerk sign-in methods
- Clerk Native API configuration
- Native OAuth redirect configuration

Therefore, do not enable real production sign-in yet.

STEP 3 — CLERK PROVIDER FOUNDATION
==================================================

Create an isolated Clerk provider implementation.

Requirements:

- Use ClerkProvider from @clerk/expo.
- Use tokenCache from @clerk/expo/token-cache.
- Use expo-secure-store through Clerk's supported token cache.
- Do not manually persist Clerk session tokens.
- Do not hardcode the publishable key.

Read the publishable key from:

EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY

IMPORTANT:

The provider must remain DISABLED unless an explicit
future activation step enables it.

Do not mount ClerkProvider in the currently active
application tree yet.

Do not interfere with the existing AuthContext.

==================================================
STEP 4 — PRODUCTION AUTH API FOUNDATION
==================================================

Prepare an isolated authenticated API client.

Requirements:

- Accept an async getToken() function.
- Retrieve the current Clerk session token.
- Attach:

  Authorization: Bearer <token>

- Use the existing production API base URL configuration.
- Do not duplicate or bypass existing URL safety checks.
- Do not persist tokens.
- Do not log tokens.
- Do not use browser cookies for authentication.

Prepare support for:

GET /api/me

Do not automatically call /api/me yet.

Do not make authenticated production requests during
this stage.

==================================================
STEP 5 — AUTHENTICATION STATE MODEL
==================================================

Prepare TypeScript types or isolated utilities for
the future production authentication flow.

Account for:

- Clerk provider loading
- Signed out
- Clerk signed in
- /api/me loading
- /api/me authenticated
- /api/me returns isAuthenticated: false
- Network failure
- Invalid or expired session
- Logout

Production /api/me fields include:

- isAuthenticated
- isAdmin
- isConcierge
- isMember
- memberTier
- isProfileComplete
- needsPlanDecision
- needsSignupPhone

IMPORTANT:

HTTP 200 does NOT automatically mean authenticated.

Only:

isAuthenticated === true

confirms backend authentication.

Do not invent additional production user fields.

Do not use local/demo authentication state as proof
of production authentication.
