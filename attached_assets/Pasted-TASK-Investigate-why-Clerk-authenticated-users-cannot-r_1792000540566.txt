TASK: Investigate why Clerk-authenticated users
cannot reach the existing Bluebird Mobile application.

IMPORTANT CONTEXT:

Bluebird Mobile already had an implemented user journey
before the Clerk-only authentication migration.

The previous intended flow was:

EXISTING USER:

Welcome
→ Continue with Phone
→ Phone authentication
→ Find existing Bluebird user
→ Home

NEW USER:

Welcome
→ Continue with Phone
→ Phone authentication
→ User not found
→ Short Registration
→ Onboarding
→ Home

The application already contains screens and logic for:

- Home
- Profile
- Membership
- Trips
- Registration
- Onboarding

We do NOT want to rebuild these features.

CURRENT PROBLEM:

Clerk phone authentication works.

After successful authentication, users see:

"Bluebird member not linked"

"No authenticated Bluebird API request has been made."

This appears to be a deliberate migration gate
introduced during Task #385.

GOAL:

Understand how to reconnect Clerk authentication
to the EXISTING Bluebird user journey.

AUDIT ONLY. DO NOT MODIFY CODE YET.

1. Locate the original authentication flow.

2. Identify how the app previously determined
   whether a Bluebird user already existed.

3. Locate the existing registration screens.

4. Locate the onboarding screens and completion logic.

5. Locate the Home screen and navigation guards.

6. Identify how Profile, Membership and Trips
   previously obtained their data.

7. Identify which parts of the previous flow
   still exist and which were changed or bypassed
   during Task #385.

8. Find the exact condition that currently
   sends Clerk-authenticated users to
   "Bluebird member not linked".

9. Identify the existing API endpoints used
   for user lookup, registration and onboarding.

10. Compare those endpoints with the documented
    production Bluebird API contract.

11. Determine whether the existing user journey
    can be reused with Clerk authentication.

12. Identify exactly what is needed to connect:

    Clerk Session
       ↓
    Bluebird User Resolution
       ↓
    Existing User → Home
       ↓
    New User → Registration → Onboarding → Home

13. Distinguish between:
    - Missing user
    - Existing user
    - User requiring onboarding
    - Backend authentication failure
    - Network failure

14. Never interpret a failed API request as
    proof that a user does not exist.

15. Do not assume a Clerk identity can be linked
    to an existing member solely by matching
    phone numbers.

16. Identify the smallest possible implementation
    needed to restore the intended user journey.
