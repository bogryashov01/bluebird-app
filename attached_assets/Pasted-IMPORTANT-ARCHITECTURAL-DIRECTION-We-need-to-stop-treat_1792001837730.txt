IMPORTANT ARCHITECTURAL DIRECTION

We need to stop treating the local API Server
as the backend for Bluebird Mobile.

The ONLY intended backend for the real
Bluebird Mobile application is:

https://bluebirdjets.com/api

This is a firm architectural decision.

AUTHENTICATION:

Clerk is the ONLY authentication provider.

The mobile app must use:

1. Clerk phone authentication
2. Clerk-managed sessions
3. Fresh Clerk session tokens from getToken()
4. Authorization: Bearer <Clerk token>
5. The real Bluebird production API

We do NOT want:

- Legacy Bluebird JWT authentication
- Local SMS authentication
- Local registration grants
- A separate mobile API server
- Mock member accounts in the real app
- A fallback to legacy authentication
- Two competing authentication systems

CURRENT PROBLEM:

The mobile app successfully authenticates
users through Clerk.

However, after authentication it displays:

"Bluebird member not linked"

This happens because the app has not connected
Clerk authentication to the real Bluebird API.
