BLUEBIRD MAIN WEBSITE — ADD SAFE DEVELOPMENT ACCOUNT STATUS CONTRACT

CONTEXT:

Bluebird Mobile uses the existing Main Bluebird API
and shared Clerk Development authentication.

The existing backend already supports:
- Clerk authentication
- User profiles
- Profile completion
- Multiple preferred airports
- Membership-independent account access

We need one missing capability:

An authoritative account registration status
for mobile post-login routing.

GOAL:

Add the smallest backward-compatible,
read-only account status contract.

STRICT SAFETY REQUIREMENTS:

1. Preserve all existing API behavior.
2. Do not rewrite authentication.
3. Do not modify Clerk configuration.
4. Do not modify database schemas.
5. Do not modify existing membership logic.
6. Do not modify profile completion rules.
7. Do not change existing API response fields.
8. Do not change the Main Website frontend.
9. Do not send SMS.
10. Do not perform profile writes.
11. Do not deploy to Production.

IMPLEMENTATION:

Prefer an additive endpoint:

GET /api/me/account-status

The endpoint must:

- Use the existing Clerk authentication middleware.
- Resolve the current Clerk user identity.
- Check profile existence by clerk_user_id.
- Reuse existing profile-completion logic.
- Reuse existing membership status logic.
- Return explicit registration status:

  new
  incomplete
  complete

- Return separate membership information.
- Return explicit 401 for unauthenticated requests.
- Return explicit 5xx for backend failures.
- Never return guest-shaped HTTP 200 on errors.
- Never create or update a profile.
- Never synchronize phone data.
- Never trigger SMS or membership operations.

SECURITY:

Do not match accounts by phone or email alone.
Use the authenticated Clerk identity.

VALIDATION:

Add focused tests for:

- Unauthenticated user
- New user
- Incomplete profile
- Complete profile without membership
- Complete profile with membership
- Backend errors
- Development/Production isolation

Run existing Main API tests and TypeScript checks.

IMPORTANT:

Before implementing, inspect the existing API
and confirm this can be added without modifying
existing response contracts.

If the change could affect Production or existing
Website behavior, STOP and report the risk.

Do not deploy anything.

DELIVERABLE:

A small, backward-compatible account-status endpoint
implemented and tested in Development only.

No other changes.
