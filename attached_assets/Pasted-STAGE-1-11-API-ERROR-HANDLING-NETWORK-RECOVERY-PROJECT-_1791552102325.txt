Focus on real user-facing problems.

==================================================
1. AUDIT CURRENT NETWORK BEHAVIOR
==================================================

Inspect the existing production readers and hooks for:

GET /api/empty-legs
GET /api/empty-legs/:id
GET /api/airports?codes=...
GET /api/airports/search?q=...
GET /api/airports/cities
GET /api/plans

Identify:

- request timeouts
- error handling
- loading states
- retry behavior
- request cancellation
- stale responses
- concurrent requests
- cache behavior

Do not rewrite working code unnecessarily.

Report confirmed issues before fixing them.

==================================================
2. NETWORK TIMEOUTS
==================================================

Ensure production-read requests cannot remain pending forever.

Requirements:

- Use bounded request timeouts.
- Prefer AbortController where supported.
- Clean up timers and abort listeners.
- Distinguish timeout from HTTP errors where practical.
- Avoid unhandled promise rejections.

Do not reuse the 8-second auth restoration timeout
automatically for every production request.

Choose appropriate values based on the existing architecture.

==================================================
3. ERROR STATES
==================================================

Verify behavior for:

- No internet connection
- HTTP 500
- HTTP 503
- HTTP 429
- Request timeout
- Invalid JSON
- Unexpected response schema
- Empty valid response

Requirements:

A failed request must not:

- crash the app
- display a blank screen
- silently load local demo data
- show fabricated production values
- trap the user in infinite loading

Use clear, neutral error messages.

Examples:

"Unable to load flights."

"Unable to load membership plans."

"Airport search is temporarily unavailable."

Provide Retry where appropriate.

Do not expose raw internal error details to users.

==================================================
4. RETRY BEHAVIOR
==================================================

Inspect existing Retry buttons.

Ensure:

- Retry starts a new request.
- Loading state is visible.
- Retry can recover after a temporary failure.
- Repeated taps do not create uncontrolled requests.
- A successful retry clears the previous error.

Do not implement unlimited automatic retries.

If automatic retries already exist, ensure they are bounded.

For HTTP 429, respect Retry-After when practical.

==================================================
5. RACE CONDITIONS
==================================================

Check rapidly changing requests.

Especially:

Airport Search:

User types:

D
DA
DAL
Dallas

Verify that an older response cannot overwrite
the latest search results.

Flight Details:

User navigates quickly between different flight IDs.

Verify that the previous flight response cannot
overwrite the newly selected flight.

Map:

Verify that stale airport-coordinate responses
cannot overwrite a newer route selection.

Membership Plans:

Verify that unmounted screens do not receive
unsafe state updates.

Use existing query/cancellation patterns where possible.

==================================================
6. OFFLINE BEHAVIOR
==================================================

Simulate network failures in Web Preview.

Verify:

- Discover shows a recoverable error.
- Flight Details shows a recoverable error.
- Airport Search shows a recoverable error.
- Membership Plans show a recoverable error.
- Map does not display fabricated coordinates.

Do not implement a full offline storage system.

If previously loaded production data remains visible
during a temporary failure, it must be clearly
distinguishable from freshly loaded data when necessary.

Never replace a production failure with demo fixtures.

==================================================
7. SCREEN NAVIGATION
==================================================

Test:

- Navigate away while a request is pending.
- Return to the screen.
- Refresh the browser during loading.
- Switch between Discover and Map.
- Open Flight Details while Discover is refreshing.
- Open Membership Plans after an API error.

Ensure:

- No navigation loops.
- No persistent loading state.
- No stale cross-screen data.
- No unhandled exceptions.
