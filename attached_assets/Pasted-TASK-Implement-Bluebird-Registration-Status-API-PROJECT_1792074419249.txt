TASK: Implement Bluebird Registration Status API

PROJECT:
MAIN BLUEBIRD WEBSITE REPLIT

MODE:
BUILD / IMPLEMENTATION

IMPORTANT CONTEXT:

We are integrating a separate Expo / React Native
mobile application with the existing Bluebird API.

The mobile app uses Clerk authentication.

The main Bluebird website already uses
Clerk Express middleware and PostgreSQL.

We have completed the architecture and
backend-contract audits.

REFERENCE DOCUMENT:

BLUEBIRD_MOBILE_BACKEND_CONTRACT.md

Read Section 5 carefully before implementation.

GOAL:

Implement ONE minimal, backward-compatible
authenticated API endpoint:

GET /api/me/registration-status

This endpoint must allow Bluebird Mobile
to reliably determine the current
authenticated Clerk user's:

- Identity
- Profile existence
- Profile completeness
- Active membership status

WITHOUT changing the existing website
authentication or registration behavior.

==================================================
REQUIREMENTS
==================================================

1. AUTHENTICATION

Use the existing global Clerk middleware.

Resolve the REAL middleware-verified
Clerk user identity.

Do not trust a user ID supplied
in query parameters or request bodies.

Do not use an impersonated/effective
identity for this endpoint.

Do not accept legacy Bluebird JWT tokens.

Return HTTP 401 when authentication
is missing or invalid.

Do not silently return guest state.

2. SUCCESS RESPONSE

Return HTTP 200:

{
  "contractVersion": 1,
  "identity": {
    "provider": "clerk",
    "userId": "<verified Clerk user ID>"
  },
  "profile": {
    "exists": true,
    "complete": false
  },
  "membership": {
    "active": false,
    "tier": null
  }
}

Use existing profile-completeness rules.

Use existing active-membership rules.

A missing profile must return:

"profile": {
  "exists": false,
  "complete": false
}

Profile existence and membership status
must be evaluated independently.

Do not classify a user as new
based only on membership.active=false.

3. ERROR HANDLING

Return explicit errors.

Missing/invalid authentication:

HTTP 401
{
  "error": {
    "code": "AUTH_REQUIRED",
    "message": "Sign in to continue."
  }
}

Temporary account-status failure:

HTTP 503
{
  "error": {
    "code": "STATUS_UNAVAILABLE",
    "message": "Account status is temporarily unavailable.",
    "retryable": true
  }
}

If an authoritative account-link conflict
is actually detected:

HTTP 409
{
  "error": {
    "code": "ACCOUNT_LINK_REVIEW_REQUIRED",
    "message": "This account needs a support review before registration can continue."
  }
}

Do not fabricate conflict detection
if the current backend has no
authoritative conflict signal.

4. SIDE EFFECTS

The endpoint must be strictly read-only.

NO database writes.

NO Clerk metadata changes.

NO phone verification.

NO SMS.

NO email.

NO Sendblue or Quo calls.

NO membership activation.

NO family invitation linking.

NO profile creation.

Do not use existing GET handlers
that perform profile self-healing
or other write side effects.

5. BACKWARD COMPATIBILITY

Do not modify the existing:

GET /api/me

GET /api/me/profile

PUT /api/me/profile

POST /api/me/signup-complete

Do not change existing website
registration or onboarding behavior.

Do not change Clerk configuration.

Do not modify the database schema
unless an existing model makes the
new endpoint impossible.

Do not change production settings.

6. API CONTRACT

Add the new endpoint to the existing
API router.

Update the relevant OpenAPI schema
and generated client contracts
using the project's established workflow.

Do not hand-edit generated files
if code generation is available.

Preserve existing API response shapes.

7. TESTING

Add focused automated tests for:

- Authenticated user with complete profile
- Authenticated user with incomplete profile
- Authenticated user without profile
- Authenticated user with active membership
- Authenticated user without membership
- Unauthenticated request
- Database failure
- Clerk identity resolution failure
- No writes or external notifications

Use mocks or isolated test fixtures.

Do not use production accounts,
production database, or real SMS.

Do not make authenticated production requests.

Do not deploy.

Do not start workflows that connect
to production services.

==================================================
DELIVERABLE
==================================================

Implement the endpoint in the
existing MAIN Bluebird API.

Provide:

1. Exact files changed.
2. Endpoint response schema.
3. Authentication implementation.
4. Test results.
5. Confirmation that existing
   website endpoints were preserved.
6. Any remaining blockers.

IMPORTANT:

This task authorizes only the
new endpoint and its supporting
contracts/tests.

Do not modify the mobile project.

Do not deploy to production.

Do not create a separate backend.

Do not weaken authentication.

Do not implement registration
or profile writes in this task.
